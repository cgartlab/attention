# 核心文档同步（提交前门槛）

## 核心文档集
**完整定义在 `judgment-criteria.md` 的"核心文档集"一节**——本文件不复述。默认集可按项目布局覆盖；覆盖后在报告里说明用了哪套。

## 门槛通过条件
**通过 = 逐条对照 diff 检查相关段落并落实到文档，不是"扫描结果为空"。** 完整定义（含"未消解的 `［待补充：…］` 算未通过"）见 `judgment-criteria.md` 的"门槛通过条件"一节。

## 知识分层：同一事实只该有一个权威位置

"文档同步"不是"往文档里加字"。先决定**这条事实该住在哪一层**，再动笔——层放错了，后面必然出现两处说法不一致。

| 层 | 只放什么 | 不放什么 |
|---|---|---|
| `AGENTS.md` / `CLAUDE.md` / 规则文件 | 下一次 agent 不看到就会犯错的边界、命令、流程 | 完整架构、评分公式、数据流细节、历史叙事 |
| `README` / `docs/**` | 系统怎么用、怎么工作、怎么运维；当前对外合同 | 一次性过程记录、已完成待办 |
| `CHANGELOG` | 面向使用者的版本叙事（分节见 `changelog-sections.md`） | 内部重构细节、无对外行为变化的改动 |
| git 历史 / commit | 过程、动机、单次事故 | 当前状态的权威描述 |

**单一权威 + 短指针**：同一事实只保留**一个**权威解释，其他位置要么删掉，要么放一行短指针（"详见 `docs/architecture.md` 的 X 节"）。禁止在两个地方各写一份完整说法——两份完整说法将来必然分叉，而分叉后无法判断哪份是对的。

> 本仓库自己踩过这个坑：`SKILL.md` 曾内联各 reference 的"速查副本"，结果 force push 的禁止范围、受保护分支名单、核心文档集三处全部漂移。**副本是唯一保证被加载的文本，于是更弱的规则成了实际执行的规则。**

**判断"该不该在这里写"**：问一句"下次谁会在什么场景读到这里？"——读它的人需要的是**行动依据**（规则层）、**理解系统**（docs 层），还是**知道改了什么**（CHANGELOG 层）？答不出来就别写。

## 先减后加

改文档时**先删过期内容，再加新内容**——顺序不能反。

理由：文档膨胀是单向的。每次改动都"顺便加一段"，几个月后权威事实会淹没在历史叙事、重复指针和已完成待办里，读者找不到现役答案（这正是"核心规则被挤没"的过载形态）。先删再写，净增长才受控。

要删 / 要合并的典型对象：

- **过期的现役说法**：文档说 A，代码已经是 B → 改写成 B，**不是**追加一句"补充：现在是 B"。
- **重复指针**：同一事实的第二、第三处完整说法 → 收敛成一个权威 + 短指针。
- **中间态叙事**："当时先这样、后来改成那样"的过程 → 归 git/CHANGELOG，现役文档只留结论。
- **已完成的待办**：还挂在"待办 / 计划"里的已完成项 → 核实后删除或改成当前约束，不留"已完成"流水账。
- **"保留作历史"但没有真实读者的段落** → 删除。历史要值得保留，需同时满足：有用途、有权威位置、有检索入口。

⚠️ **先减后加 ≠ 大删大改**：拿不准某段是否还有用的，**列入计划表让用户裁定**，不擅自动手。删掉别人还在依赖的内容，比留着一段冗余更糟。

## 差异驱动更新法
1. 跑 `core_docs_relevance_scan`，拿到三类信号：
   - `changed_files` / `changed_basenames`：本次变更集里变了哪些文件。
   - `docs_mentioning_changes`：哪些核心文档**字面提及**了这些变更文件名。
   - `docs_stale_candidates`：`exists=true`、本次没碰、也没提到任何变更文件的核心文档 → **"请人工确认是否需要更新"的清单**。
   - ⚠️ 扫描是**低精度提示，不是裁决**：`docs_mentioning_changes=[]` **不代表**文档已同步。它只做变更文件 basename 的字面匹配，文档只写函数名/命令名而不写文件名时它恒为空——而那恰恰是最该补文档的情况。`docs_stale_candidates` 才是要你逐份过一遍的清单。
2. 对 `docs_mentioning_changes` 命中的文档 **+ `docs_stale_candidates` 里的每一份**，逐项对照 diff：
   - 变量/导出改名 → 文档里的旧名改新名。
   - CLI 命令变 → 文档示例同步。
   - 文件移动/删除 → 文档路径同步。
   - 新增能力 → 文档补一段（仅当 diff 明确体现该能力）。
   - 看起来相关但 diff 没触及 → 不改（写"无需更新"并说明理由）。
3. 不得新增事实：文档里出现的数字、日期、人名、原话、性能指标，必须能在 diff 里找到落点（或来自与本次变更无关的客观文件事实）。**不得拿"待更新的文档自身"当出处**（见下方"溯源要求"）。找不到 → 标 `［待补充：…］` 占位符，不替作者圆上。
4. CHANGELOG 单独走 `release-versioning.md`。

## 溯源要求（每条条目都要能被追到 diff）
- 每条写进 CHANGELOG（或文档）的条目，必须能追溯到本次 diff 里的**具体文件 / 符号**，或一条 **commit SHA**。写不出落点的内容不能作为条目存在。
- **追不到出处的 → 改标 `［待补充：…］` 占位符**，既不要删掉（那会把"已知缺一块"变成"看起来完整"），也不要编一个出处。
- **区分"内容来源"与"溯源指针"**：内容只能来自 diff 事实（改动的文件/符号/用户可见字符串）；`—— ref: src/a.js:add()` 或 `—— commit: a1b2c3d` 只是**指针**，用来让人能回查。**commit message、PR 标题、issue 链接是"作者声明"而非 diff 事实，不能当内容来源**——它们只是 `release_signals` 的输入（判断"要不要发版"），不是条目文案。CHANGELOG 的完整采信范围见 `changelog-sections.md` §三。
- **出处不得是"待审计/待更新的文档自身"**：不能拿"README 里已经这么写了""上一版 CHANGELOG 这么写的""注释里提过"当依据——那是循环自证，源头可能本来就是错的。合法出处只有：本次 diff、承载它的 commit、（与本次变更无关的）客观文件事实（如 `package.json` 的真实字段值、git tag）。
- 反例（禁止）：`- 修复了并发崩溃问题（依据：CHANGELOG.md 第 12 行）`——依据文件就是正在写的文件本身。

## `［待补充：…］` 的语义（占位符，不是失败标记）
- 它是**占位符**：模型识别到"这里需要有内容"，但 diff 无法支撑（数字、日期、人名、性能指标、动机原话等）。写进去是为了**不编造**，同时留下一个明确的工作点。
- **不是失败标记**：它不表示这次立正失败了，也不表示该文档整体不可用；它标记的是**一条需要用户补充的具体信息**。
- **用户应补充，而不是删除**：删掉占位符等于把"已知缺一块"伪装成"完整"。报告里要把占位符逐条列出来告诉用户补什么。
- **含未消解占位符的文档，要么不进本次提交，要么在 PR body 的"文档与版本一致性"一节显式列为阻塞项**——二选一，不能当没看见直接推出去。

## 反幻觉红线
- 不编造版本号、不编造 CHANGELOG 条目、不编造文档未支撑的功能。
- 推测标明为推测，不写成事实。
- 改稿涉及不可互换语义（数据结果/意义评价、功能/目标、性能/成本收益）时：删修饰可以，换说法不行。

## 什么时候不更新文档
- 变更只是格式化、重排、注释、纯内部重构且无对外行为变化 → 不动文档，但报告"本次无需文档更新"并给出理由（理由要落到 diff 上，不是"扫描结果为空"）。
- 拿不准影响面 → 在计划门槛里列出，让用户裁定，不擅自改。

## 两类最容易被漏掉的核心文档

- **仓库自带的开发计划 / 任务清单**（`docs/DEVELOPMENT-PLAN.md`、`ROADMAP.md`、`TASKS.md` 一类）：新增阶段或能力后，同步它的**进度、待办、阻塞（附证据）与可判定验收条件**。漏了这一步，下一个读者（包括下一次立正）看到的是"没有这件事"；而"阻塞"要写成真实状态（如 CI 作业未启动 → `BLOCKED`，不是"没做"）。
- **文档里的命令与参数示例**：它们是可执行断言。重构过 CLI / 脚本入口 / 文件名后，把示例命令抽出来实跑一次，或至少与 `--help`、argparse 的实际选项逐条比对。文档写着实现里不存在的 flag（`--start-date` vs 真实的 `--start`），照着执行必然失败，而且没有任何 CI 会发现——文档漂移比代码 bug 更贵，因为它专挑信任它的人。

**数字类陈述会各自生长**：断言条数、checks 总数、fixture 数常同时出现在 README / AGENTS / VALIDATION / 计划文档里，改一处就要全仓 grep 同步（见 `references/common-pitfalls.md` 第 17、19 条）。
