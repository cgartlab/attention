# PR 描述结构

按本结构组织 `gh pr create --body`，让评审者一眼看清动机、改动、验证与一致性保证。

```
## 动机
<为什么做这个改动？解决了什么问题/带来什么能力。一两句。>

## 改动
- <要点 1：做了什么>
- <要点 2：做了什么>
- <要点 3：做了什么>

## 验证
- <跑了哪些测试/lint/build，结果如何。失败且与本变更无关的在此说明。>

## 文档与版本一致性
- 核心文档：<已同步 / 无需更新 / 待补充项列出>
- 版本：<未涉及 release / 已一致 bump 至 vX.Y.Z / tag 计划>

## 关联
<可选：Closes #N，或相关 issue/PR 链接>
```

## 红线
- 只写 diff 真实支撑的改动；不编造未实现的能力。
- 验证结果如实：绿就写绿，失败就写失败并说明是否本变更引入。
- 不编造 issue 链接。
