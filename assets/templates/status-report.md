# 立正收尾报告模板

每次"立正"结束，按本结构向用户汇报。**主叙事全部用大白话**——读者是项目作者（可能是刚入行的开发者）。字段名 / 命令串 / JSON 键一律不进主叙事；要留就放进末尾"📋 技术细节"小节。主叙事必须能脱离技术细节独立读懂。

## 报告结构

```
## 立正汇报

**可发布判定**：<READY / NOT READY / BLOCKED> —— <一句大白话，说清现在能不能发>

### 这次帮你做了什么
- <大白话：发现了什么 → 做了什么 → 现在怎样。一条一件事>
  例：我发现一个已经合并完、没人再用的旧分支 feature/old-login，帮你删掉了，分支列表干净多了。
- <没做的事也用大白话说为什么>
  例：项目还没连上 GitHub 远程，所以"同步最新代码""开 PR"这两步先跳过——等你连上远程我再帮你补。

### 你接下来可以做什么（按重要性排）
1. **【重要】<建议标题，大白话>**：<现状> → <该做什么> → <为什么对项目好>
   例：**给项目连个 GitHub 远程**：代码现在只在你电脑上，没备份没法协作 → 在 GitHub 建空仓库、把地址给我（https://***@github.com/<你>/<仓库>.git） → 连上后能备份、能开 PR，项目才算"活"起来。
2. **【建议】<建议标题>**：……

### PR（如果有）
- <PR 链接，或"还没开，因为…下一步…"，大白话；链接里的远程地址用脱敏形式>

---

### 📋 技术细节（可选，给想核对的人；新手可跳过）
> 只放原始信号供核对，主叙事必须能独立读懂。没有就写"无"。
- 远程：<remote_url_masked，脱敏形如 https://***@github.com/user/repo.git>
- 默认分支 / 本地变更 / 已合并分支候选 / 陈旧未合并 / 受保护 / 版本文件一致性 / 涉及 release / 未推送提交与分支
- 本次用的阈值与覆盖口径（如陈旧阈值、核心文档集覆盖）
```

## 可发布判定（必须写，就在最上面）
一句话回答"这个项目现在能发吗"，用人话写，不用术语：

| 判定 | 大白话说法 | 什么情况下给 |
|---|---|---|
| **READY** | "可以发了：改动都提交了，文档和版本号对得上，没发现拦路的问题。" | 工作区干净、文档与版本门槛都过、没有阻塞项 |
| **NOT READY** | "还差几步：东西没齐，我把差的列在下面了，补齐就能发。" | 有明确、可执行的待办（缺文档、版本没对齐、测试没跑通等）——**不是失败**，是"还能推进" |
| **BLOCKED** | "卡住了：有件事我自己解决不了，需要你先处理，处理完我继续。" | 有需要用户决策或外部条件才能推进的阻塞（冲突、凭据、需要用户裁定是否 bump、未消解占位符） |

- 判定与"下一步建议"必须一致：给 NOT READY/BLOCKED 就一定要列出差在哪。
- 拿不准 → 选更保守的那个（NOT READY 或 BLOCKED），不要选 READY。

## 关键项分级（CRITICAL / WARNING / SUGGESTION）
主叙事里每条发现和建议都带一个级别标签，让用户一眼分出轻重：

- **CRITICAL（拦路）**：不处理就不能发/会丢东西。例：未跟踪的半成品文件将被误删、版本号三个文件互相矛盾、本变更引入了红灯测试、含未消解 `［待补充：…］` 的文档要进提交。
- **WARNING（该处理）**：能发但不健康，建议这次就修。例：CHANGELOG 缺条目、`unpushed_commits=null`（没连远程，无法判断是否已推送）、陈旧但未合并的分支堆积。
- **SUGGESTION（可选改进）**：锦上添花。例：补 README 的安装示例、给旧分支加命名规范、补测试。

规则：
- **CRITICAL 必须写进 BLOCKED/NOT READY 的理由里**，不能只出现在技术细节。
- 级别允许为空（这次没发现问题就写"没发现拦路问题"）。
- 不要把所有东西都标 CRITICAL——那等于没分级。

## 写法正反例（对照，别又写成字段名堆砌）

> ❌ **别这样**（字段名堆砌，新手看不懂）：
> 判定：干净态。local_merged_candidates=[]，is_github=false，version_files=[]。pull --ff-only 未执行（无 upstream）。next_steps：配置远程；补 CHANGELOG。

> ✓ **要这样**（大白话，用户立刻知道干啥）：
> **可发布判定：NOT READY** —— 还差几步，东西本身没问题。
> 你的项目现在是干净的，没有未保存的改动，也没有需要清理的旧分支。不过有两件事可以做得更好：
> **【建议】连个远程仓库**：代码现在只在你电脑上（远程地址还没配），没备份也没法在线协作……
> **【建议】补更新记录**：项目标了版本号 0.1.0，但没有任何更新记录，别人看不出每版改了什么……

## ✅ 你如何复核（把命令交给用户，让他能自己验证）

报告里凡是"我查过了 / 我改了"的结论，都配一条**用户自己能跑**的命令：能复制粘贴，并写清"看什么算对"。

按报告内容裁剪（不要全塞）：

| 报告里说了什么 | 你可以这样复核 | 看什么算对 |
|---|---|---|
| 现在没有未提交改动 | `git status --short` | 没有输出 = 干净 |
| 我提交了什么 | `git log --oneline -3` / `git show --stat HEAD` | 提交信息与文件列表和报告一致 |
| 我删了哪个分支 | `git branch --list` | 该分支已不在；未合并的分支仍在 |
| 版本号已对齐 | 打开那两个版本文件，或 `git diff HEAD~1 -- <版本文件>` | 两处版本号相同 |
| 文档已同步 | `git diff HEAD~1 -- README.md CHANGELOG.md` | 改动能对上这次代码变化 |
| 测试是绿的 | 报告里给出的那条测试命令 | 退出码 0、输出符合预期 |
| 远程没连上 | `git ls-remote origin` | **报错 = 确实没连上**，不是"远程没有内容" |

规则：
- 复核命令**只读**，不得含 push / 删除 / 打 tag 之类动作。
- 命令必须在本环境**真的能跑**；跑不了的不要写（例如需要内网时，就直说"这条我也没验证"）。
- 复核结果与报告不一致时，以命令输出为准，并说明差异——不要为了让报告好看而挑命令。
## 红线
- 主叙事每一句大白话；不编造；没做就说没做 + 为什么（大白话）。
- **"没查成"必须写成"没查成"**：远程连不上、`gh` 没登录、脚本失败，都要写"这步没查成/没跑成"，**不得**写成"没有"。
- 字段名 / 命令串 / JSON 键 不进主叙事，只进末尾"📋 技术细节"。
- **远程 URL 一律脱敏**（用 `remote_url_masked` 形态），报告里不得出现带凭据的地址。
- 技术细节是"可选核对"用，主叙事必须能独立读懂。
- 可发布判定必须在最顶上，且与下面的待办一致。
