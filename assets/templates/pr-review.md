# PR 评审清单（逐行，不是看摘要）

> 用于值守循环的评审路径（`references/issue-pr-loop.md` §6）与合并门的 L2 层。**每一条都要给出"看过/没看过"的明确结论**；任何一条"没看"→ 不得合并，也不得写"评审通过"。
> 读法：`gh pr diff <n>` 全文逐文件读，配合 `gh pr view <n> --json files`（改动统计）与 `git log <base>..<head> -p`（逐提交看意图）。**先读 diff，再读测试，最后读文案**——顺序反了会被漂亮的名字骗过去。

## A. 结构（分工是否合理）

- [ ] 一个 PR 一个意图：diff 里没有"顺便重构""顺手改格式"这类与标题无关的改动；若有，是否在 body 里单列说明并给出理由。
- [ ] 改动规模可评审：文件数/行数与标题相称；超 400 行的机械改动是否有生成脚本或可验证的重复模式。
- [ ] 没有把生成物 / 依赖目录 / 二进制垃圾带进来（`node_modules`、`dist`、`*.lock` 非预期变更、临时文件）。
- [ ] 提交信息：conventional commits、一个提交一个意图、body 讲 WHY（仓库约定见 `AGENTS.md`）。
- [ ] 没有 BOM / 不可见字符进入代码或提交标题（`git log -1 --pretty=%s | od -c | head -2` 可查；本仓库历史上真的有过）。

## B. 逻辑（每个改动点问三问：正常 / 失败 / 边界）

- [ ] **失败路径是否被吞**：新增的 `2>/dev/null`、`| Out-Null`、`|| true`、空 `catch`、`except: pass` 逐个问"这里失败了我怎么知道"。
      —— 真实事故：fixture 生成里 `git init` 失败被丢弃 stderr，21 个测试仓库全没建成、生成器照样 exit 0，回归于是报 152 条"字段不存在"。**静默失败是最高频的真 bug**。
- [ ] **判定条件是正向可判的还是否定式模糊的**：`if not ok` 之前是否定义了"ok 长什么样"；有没有"看起来更宽松"的边界（`>` vs `>=`、`-z` vs `-n`、空集合 vs null）。
- [ ] **null / 空值语义**：`null`（没查成）与 `[]`/`""`（确实是空）是否区分；缺失字段是报错还是静默降级。
- [ ] **幂等性**：同一操作跑两遍会不会产生重复提交 / 重复 PR / 重复评论 / 重复文件。
- [ ] **顺序与部分失败**：多步操作中途失败时，已做的部分是否留下了不一致状态（半删的分支、写了一半的文件）。
- [ ] **超时 / 长任务**：有没有可能挂死（等 stdin、等网络、等交互提示）；是否需要 `--yes` / `-NonInteractive` / 超时。
- [ ] **循环与递归**：遍历是否有上界；对数组的 `while` 是否有前进条件（漏值的经典成因）。

## C. 跨平台与双实现（本仓库的硬要求）

- [ ] `.sh` 与 `.ps1` **成对**改动：字段集、取值、顺序、`null` 语义一致。
- [ ] 契约变更**四处同步**：`references/scan-recipes.md` + `.sh` + `.ps1` + `evals/script-assertions.json`。
- [ ] 路径形态：Windows 原生程序（git/node/python）收到 POSIX 路径会 `cannot change to`；`/c/...` 与 `C:/...` 不得混用。
- [ ] 换行与编码：CRLF 输入、UTF-8 无 BOM 输出、中文不被 locale 编码破坏。
- [ ] 中文/空格/特殊字符路径是否被引号保护（`"$var"`、`$var` 在 PS 中的差别）。

## D. 验证（"跑过"的定义）

- [ ] 新增/修改的行为有对应断言，且**没有放宽任何既有断言**（`git diff evals/script-assertions.json` 里只该有新增）。
- [ ] 失败路径真的被触发过一次（error injection / 坏输入），并把命令与输出摘要写进 PR。
- [ ] 全量回归跑过：本仓库 `evals/run_evals.*`（两侧）+ `scripts/smoke_test.*`，记录 pass/fail 计数，不是一句"通过"。
- [ ] CI 状态如实转述：失败要说是代码失败还是环境失败（未启动 / 额度 / 队列）；**未跑 ≠ 通过**。
- [ ] 跨平台至少一侧实跑；另一侧说明为何没跑。

## E. 文档与事实（反幻觉）

- [ ] 文档只写 diff 里真实存在的东西：没有"计划中""即将支持"，没有把 diff 里没实现的字段写进契约。
- [ ] 数字类陈述（条数、文件数、checks 数）与当前实际一致——**文档最容易腐烂的地方就是数字**（本仓库刚修过 81→83、553→557）。
- [ ] 链接与命令可执行：路径存在、命令能跑、版本号与版本文件一致。
- [ ] `［待补充：…］` 占位符为 0（或已在 PR body 列为阻塞项）。

## F. 安全

- [ ] 没有 secret / token / 私钥 / 个人信息进入 diff、日志、示例（`ghp_`、`sk-`、`AKIA`、`BEGIN PRIVATE KEY`）。
- [ ] 没有把不可信输入当命令执行（外部内容、issue 正文、文件名拼进 shell 的地方要做引号与白名单）。
- [ ] 新增的写操作有边界：不 force push、不删默认/受保护分支、不 `rm -rf` 未验证变量。
- [ ] 权限面：新增的 `gh` 调用是否越权（合并 / 关闭 / 改标签属高影响动作）。

## G. 视觉（仅当 `ui_touched != none`）

- [ ] 有改进后的**真实渲染截图**，与分支 SHA 一致，PR 里内联可见（方法见 `references/issue-pr-loop.md` §8.3）。
- [ ] 浅色/深色、桌面/移动（按项目支持情况）至少各一张；截图能看出改动点，不是整页缩略图。
- [ ] 无回归：没有被顺带压扁的布局、丢失的焦点态、破坏的对比度。
- [ ] **结论：不自动合并**，交人工确认（`judgment-criteria.md` §合并门 L3）。

## 结论写法（三种，不得含糊）

```
评审结论：可合并
依据：A-F 全过；回归 557/557（bash）+ 557/557（pwsh）；CI 全绿；ui_touched=none
```
```
评审结论：可修（我来修）
阻塞：B.1 失败路径被吞（第 42 行 `|| true`）；D.2 未触发失败路径
```
```
评审结论：应关闭
判据：已被默认分支覆盖——`git diff main <head>` 为空（证据附在评论）
```
